# 邀请码有效状态与生效时间

## Goal

让管理员准确判断每个邀请码当前能否兑换，并在创建单码或批次时分别设置生效时间和兑换截止时间，同时清楚区分邀请码生命周期与已激活设备的访问状态。

## Background And Confirmed Facts

- 当前邀请码已经实时派生 `active`、`redeemed`、`expired`、`revoked` 四种状态，管理端显示为“待兑换 / 已兑换 / 已过期 / 已撤销”；状态不是数据库中的静态布尔值（`server/access/src/store.ts:16`、`server/access/src/store.ts:135`、`server/access/src/views/html.ts:72`）。
- 兑换在 SQLite 原子条件更新中校验未撤销、未超过 `redeem_by` 且仍有兑换次数，过期邀请码确实无法兑换，不只是界面文案（`server/access/src/store.ts:488`）。
- 创建接口目前不接收时间参数，所有邀请码固定立即生效并在创建后 7 天停止兑换（`server/access/src/constants.ts:1`、`server/access/src/store.ts:204`、`server/access/src/routes/adminRoutes.ts:37`）。
- 邀请码自然过期只影响新的兑换；已激活设备使用独立的 400 天滚动会话，只有会话到期、单独撤销会话或撤销所属邀请码时才会失效。该行为已有明确产品约定和自动化测试（`.trellis/tasks/07-30-secure-invite-access/prd.md:20`、`.trellis/tasks/07-30-secure-invite-access/prd.md:22`、`server/access/tests/store.test.ts:282`）。
- 管理端已经单独列出设备会话的“有效 / 已过期 / 已撤销”状态，但邀请码列表没有直接显示“当前可兑换：是 / 否”，容易让“已兑换但设备仍有效”产生歧义（`server/access/src/views/html.ts:116`、`server/access/src/views/html.ts:159`）。

## Requirements

### R1. Canonical Invite Availability

- 服务端实时计算邀请码生命周期，新增 `scheduled`（未生效），保留 `active`、`redeemed`、`expired`、`revoked`。
- 服务端返回只读派生字段 `redeemable`；仅当邀请码处于 `active` 状态时为 `true`。
- `redeemable` 不持久化为会随时间失真的布尔值；API、管理页和兑换事务必须共享同一套边界语义。
- 状态优先级固定为：已撤销、已用尽、未到生效时间、超过截止时间、待兑换。

### R2. Configurable Schedule

- 单码与批量创建都支持分别设置生效时间和兑换截止时间，同一批次内所有邀请码共享一个窗口。
- 两个时间均未设置时立即生效、7 天后截止；只设置生效时间时在生效后 7 天截止；只设置截止时间时在创建时刻生效。
- 生效和截止边界均包含在可兑换窗口内，截止时间必须严格晚于生效时间。
- 创建请求使用带时区的 ISO 8601 时间，数据库使用 Unix 毫秒；管理页按浏览器本地时区输入和展示，并明确显示时区。
- 服务端拒绝无效日期、无时区日期、超过 JavaScript `Date` 安全范围的日期及倒置或零长度窗口，失败时不得产生部分写入。
- 已创建邀请码的窗口不可编辑；需要变更时由管理员撤销后重新生成。

### R3. Non-Bypassable Enforcement

- 兑换事务增加“当前时间不早于生效时间”的原子条件，并保留截止、撤销和剩余次数条件。
- 未生效、过期、撤销、已用尽、不存在和畸形邀请码对普通用户继续返回相同失败文案。
- 管理 API 可以向已认证管理员返回精确状态，但不得返回邀请码哈希、会话令牌或已离开一次性创建响应的邀请码明文。
- 并发兑换、单码幂等创建和批次 payload-bound 幂等保证不能因时间字段退化。

### R4. Admin Observability

- 邀请码列表展示“当前可兑换：是 / 否”、生命周期、生效时间、兑换截止时间和有效设备数量。
- 状态筛选与计数器增加“未生效”，创建后的即时插入、撤销更新和批次操作必须同步新状态。
- 管理端继续单独展示设备会话状态，避免把“邀请码不可兑换”解释为“已激活设备已失效”。
- 单码和批量创建表单使用同一时间规则，并在提交前显示本地时区和可读窗口摘要。

### R5. Compatibility And Operations

- 数据库迁移以 `created_at` 回填历史邀请码的生效时间，升级前后的状态和兑换结果保持一致。
- 旧管理调用不传时间仍成功，并保持立即生效、默认 7 天截止。
- 数据库迁移后临时回滚旧应用时，旧代码仍能创建立即生效的邀请码；再次升级后时间数据保持正确。
- 备份、恢复、CLI 列表、部署校验和生产迁移覆盖新增字段。

## Acceptance Criteria

- [ ] 未来生效的邀请码在管理端显示“未生效”和“当前不可兑换”，生效前提交失败且不创建会话。
- [ ] 生效边界与截止边界时刻可以兑换；截止边界后的下一毫秒不可兑换，列表状态与事务结果一致。
- [ ] 待兑换、未生效、已兑换、已过期、已撤销五种状态及 `redeemable` 均有服务层和 HTTP 层测试。
- [ ] 管理员可以为单码和 1 至 50 个码的批次设置窗口；整批共享设置，非法窗口返回 HTTP 400 且数据库零写入。
- [ ] 省略双时间或任意单个时间时按 R2 生成确定的默认窗口；同一幂等请求重试不因服务器时钟推进产生冲突或重复记录。
- [ ] 历史数据库升级、旧应用回滚创建、再次升级和备份恢复后，邀请码窗口与行为均正确。
- [ ] 邀请码自然过期不终止已激活设备会话；撤销邀请码仍立即级联撤销其设备会话。
- [ ] 管理端能直接区分“邀请码当前不可兑换”和“其已激活设备仍有效”，且不暴露任何秘密字段。

## Out Of Scope

- 修改已创建邀请码的生效时间或截止时间。
- 用邀请码自然过期自动踢出已经激活的设备。
- 改变设备会话的 400 天滚动续期策略。
- 使用定时任务批量改写状态；所有时间状态在读取和兑换时实时计算。
- 增加邮件发送、公开状态查询或面向普通用户的精确失败原因。
