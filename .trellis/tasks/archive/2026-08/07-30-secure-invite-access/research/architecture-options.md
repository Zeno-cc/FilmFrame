# 邀请码架构选型

## 方案 A：本机签名的离线长令牌

本机保存 Ed25519 私钥，生成包含版本、随机 `jti`、受众、签发时间和过期时间的签名令牌；服务端只保存公钥并验证签名。

优点：生成邀请码时不需要连接服务器；服务器无法伪造新的邀请码。

代价：可粘贴令牌通常较长；需要安全备份和轮换私钥；若要求一次性、撤销和会话管理，服务端仍需要持久化状态，因此整体并不真正“无状态”。

## 方案 B：服务端状态化邀请码与会话（最终选型）

鉴权服务使用 CSPRNG 生成至少 128 bit 熵的 Crockford Base32 邀请码，只在生成成功响应中显示一次。服务端规范化后仅持久化 SHA-256 哈希、标签、过期时间和最大兑换次数。

服务端数据库不保存原码。兑换时在事务中检查哈希、有效期、撤销状态和剩余次数，原子消费后签发随机会话。生成、查询和撤销由受 Google + Passkey 双重保护的公网管理端提供，同时保留 SSH 命令作为应急通道。

优点：邀请码短、输入体验好；一次性、过期、撤销、审计和会话级联撤销直接明确；手机和桌面均可管理；不需要维护签名私钥轮换。

代价：增加鉴权服务、SQLite、Cloudflare Access 和公网管理面。服务器本身属于可信边界，若服务器完全失陷，任何源站门禁方案都无法继续保证访问控制。

## 方案 C：Cloudflare Worker + D1 门禁

在 Cloudflare Worker 中验证邀请码、保存消费状态并在缓存命中前拦截全部请求，源站再通过独立条件拒绝直连。

优点：鉴权靠近边缘，能在回源前拒绝匿名请求。

代价：引入 Cloudflare Worker/D1 的第二套部署、状态和密钥管理；仍需源站二次保护。对于已有 1Panel/OpenResty + 单服务器部署，MVP 维护复杂度高于方案 B。

## 已确认基础方案

项目所有者确认采用服务端状态化邀请码和服务器生成器，不采用完全离线长令牌。手机或任意设备的公网管理必须在本期上线。早期曾考虑延期管理员邮箱登录并自建 Passkey；该阶段性约束已被后续决定取代，最终方案是 Cloudflare Access 白名单 Google 登录与 Independent MFA WebAuthn 同时通过，项目内不自建管理员 OAuth 或 Passkey 主登录。

## 服务器生成器的访问边界

### 仅回环监听 + SSH 隧道（保留为应急通道）

管理页面和生成接口只监听服务器 `127.0.0.1` 或私有容器网络，不配置公网路由。项目所有者先建立 SSH 本地端口转发，再用自己电脑浏览器打开管理页。

优点：没有公网管理入口；复用现有 SSH 信任边界；无需增加管理员密码、第三方身份系统或公开管理 API。页面仍可提供生成、复制一次、查看状态和撤销操作。

代价：使用前需要建立 SSH 隧道，手机或陌生电脑不方便访问。

### 独立管理子域 + Cloudflare Access（最终选型）

管理页放在独立子域，仅通过 Cloudflare Access 的管理员身份验证后进入；源站还必须验证 Cloudflare/Access 身份并拒绝直接 IP 访问。

优点：可从手机或任意设备访问，使用体验更接近普通后台。

代价：增加第三方身份、边缘策略、源站防直连和恢复流程；管理面暴露到互联网，风险与维护成本高于 SSH 隧道。

源站不能只检查 `CF-Access-*` 头是否存在，而必须验证 Cloudflare Access JWT 的签名、issuer、audience 和有效期。管理服务只监听回环或私有容器网络，由本站专属 OpenResty vhost 代理；即使攻击者直连源站并伪造 Host，也无法生成有效 JWT。

Cloudflare Access Google 身份与 Independent MFA 未全部配置并验证前，独立管理子域不得上线；“先公开页面、以后补登录”会让任何访问者拥有签发权限，不能作为过渡状态。

### 独立管理子域 + 自建 WebAuthn Passkey（已拒绝）

管理服务使用 WebAuthn 注册并验证平台通行密钥。首次注册前必须在 SSH 中创建短时、单次使用的引导挑战；注册成功后立即消费并关闭引导入口。服务端只保存 credential ID、公钥、sign counter、transport 等验证所需数据，不保存管理员密码或私钥。

优点：不依赖邮箱或静态密码，抗钓鱼，手机与现代桌面浏览器原生支持；同步型通行密钥可由操作系统密码管理器跨设备使用。

代价：实现和端到端测试复杂度高于 Cloudflare Access；需要设计 SSH 恢复流程，并明确 RP ID、HTTPS、user verification、挑战时效、凭证撤销和会话生命周期。

### 明确拒绝

- 不使用一个静态管理员密码直接保护公网生成页。
- 不允许普通邀请码会话访问签发接口。
- 不把生成密钥、管理员令牌或固定邀请码放进前端 JavaScript、Cookie 可读字段或 `localStorage`。

## 推荐服务端形态

- 独立、轻量的认证服务，仅监听回环或私有容器网络，不修改 FilmFrame 渲染代码。
- SQLite 持久化邀请码哈希、原子兑换次数、会话哈希、过期和撤销状态；单实例足够，启用 WAL、持久卷、受限权限和备份。
- OpenResty `auth_request` 保护所有应用资源，只公开邀请页、兑换接口和必要健康检查。
- 会话使用服务端状态和 `__Host-` HttpOnly Cookie；不在 Cookie 或浏览器存储中携带可伪造权限。
- Cloudflare 对此 hostname 绕过共享缓存并在上线时清理旧缓存；源应用端口仅绑定 `127.0.0.1`。

如未来增加“服务器不可达时也必须签发”的需求，再单独评估方案 A 的离线签名与密钥轮换，不在 MVP 中同时维护两套邀请码协议。
