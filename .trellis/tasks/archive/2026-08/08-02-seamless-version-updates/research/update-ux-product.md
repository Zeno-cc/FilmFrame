# FilmFrame 版本更新产品与交互研究

## 结论

FilmFrame 最合适的不是“打开自动更新”，而是管理后台内的**手动确认、服务器持续执行、失败自动回滚**。日常体验可以做到一键更新，但安全门禁不能被省略：候选版本必须来自固定 GitHub 仓库的正式 Release，更新前先完成预检和数据库备份，切换后通过完整健康检查才算成功。

首版默认策略建议：

- 管理后台每 6 小时静默检查一次稳定版，进入“版本与更新”页面时立即刷新；检查失败不影响主站。
- 只提示正式 Release，不跟随 `main`、预发布版本或 `latest` 镜像。
- 默认不无人值守安装；管理员看完变更摘要后点击一次“更新到 x.y.z”。
- 构建和预检期间旧版本继续提供服务，只有最终切换产生短暂重连。
- 任一上线门禁失败自动回滚；管理员无需在故障窗口里临时判断。
- 更新任务脱离浏览器运行，关页、刷新、手机锁屏都不会中止；再次进入页面自动恢复进度。

这比“完全自动更新”更适合一台承载多个 1Panel 站点的个人服务器，也符合当前 Cloudflare Access 单管理员入口、Docker Compose、不可变 release 目录和 SQLite named volume 的边界。

## 对参考项目的取舍

用户希望参考 `james-6-23/codex2api` 的丝滑版本更新体验。值得吸收的是：在管理界面直接看见新版本、变更内容、状态和更新入口，减少 SSH 操作。FilmFrame 不能照搬“前端按钮直接执行脚本”或仅凭容器自身覆盖更新的做法，因为它还承担邀请码门禁、SQLite 持久数据、Cloudflare Access 管理认证和 1Panel/OpenResty 多站点隔离。

因此借鉴的是**低摩擦的产品体验**，不是未经验证的部署实现。可信检查、锁、备份、构建、切换、验证和回滚都必须在服务器端完成。

## 信息架构

在现有管理后台顶部增加轻量导航：

- 邀请与设备
- 版本与更新

“版本与更新”页面分为三块，首屏只呈现当前最重要的信息：

1. **版本概览**：当前版本、运行状态、最近检查时间、候选稳定版。
2. **更新任务**：没有任务时显示变更摘要和更新按钮；有任务时显示阶段进度和结果。
3. **更新历史**：最近 20 次更新、回滚和失败记录，可按需展开。

管理首页只在有新稳定版时显示一个克制的“发现新版本”提示和导航圆点，不弹窗、不遮挡邀请码操作。普通邀请码用户页面完全不显示版本信息，也不能访问相关 API。

## 核心页面设计

### 无新版本

显示：

- 当前版本：`1.0.0`，附短 commit（例如 `dffcf45`）
- 状态：运行正常
- 最近检查：具体时间
- “已是最新稳定版”
- 次要按钮：“重新检查”

不要把 Docker 镜像名、服务器路径、GitHub token 状态等运维细节放在常态首屏。

### 发现新版本

候选卡片显示：

- 版本号与发布日期
- 3–6 条人工整理的中文变更摘要，按“新功能 / 修复 / 安全”分类
- 兼容性提示：是否包含数据库迁移、预计切换影响
- “查看完整发布说明”外链
- 主按钮：“更新到 1.1.0”
- 次要按钮：“稍后处理”

如果只是修订版且无数据库迁移，文案可写“预计仅短暂重连”；不要给未经历史数据支撑的精确完成时间。

点击更新后先进入**确认页/抽屉**，服务器同步执行快速预检并逐项显示：来源可信、磁盘空间、生产配置、数据库可备份、当前无其他任务。全部通过后，主按钮变为“开始更新”。这是一次连贯流程，不连续弹多个确认框。

仅以下高风险操作需要更强确认：降级、手动回滚、跳过版本、跨重大版本。首版不提供“跳过门禁”。

## 更新中的丝滑体验

不要用一个不断匀速增长的假进度条。使用真实阶段时间线：

1. 获取并校验版本
2. 构建新版本
3. 备份门禁数据
4. 准备切换
5. 切换服务
6. 健康验证
7. 完成

每个阶段只有“等待 / 进行中 / 成功 / 失败”四种状态；顶部可以用基于已完成阶段的离散进度条作为视觉辅助。当前阶段显示已用时间和一句人话说明，例如“正在构建新容器，现有网站仍可使用”。

交互规则：

- 点击开始后立即返回任务 ID，按钮变为“更新进行中”，防止重复提交。
- 服务端持有全局部署锁；其他设备访问时看到同一任务，而不是再出现更新按钮。
- 页面通过事件流获取状态，断线时自动退化为短轮询。
- 切换导致管理端短暂不可达时，页面显示“服务正在切换，将自动重连”，指数退避重连，不把网络错误误报为更新失败。
- 刷新或离开页面不会取消任务。再次打开时由服务端任务状态恢复完整时间线。
- 浏览器关闭前不弹“确定离开吗”，因为任务本就应在后台持续。
- 更新进行中禁止再次更新和手动回滚；允许安全地关闭页面。

首版不提供“取消更新”。构建/预检阶段虽然理论上可取消，但取消与回滚语义容易混淆；保持单一、可靠的完成路径更安全。后续如确有长时间构建需求，再增加仅限切换前的“停止准备”。

## 成功、失败与回滚

### 更新成功

用明确结果替代泛化的“操作成功”：

> 已更新至 1.1.0。主站、邀请码入口和管理入口验证通过，门禁数据保持完整。

同时显示完成时间、总耗时、旧版本和新版本。提供“查看变更”和“查看更新记录”，不要求管理员手动刷新。

### 失败且自动回滚成功

这是产品必须优先处理的状态：

> 1.1.0 未通过健康检查，已自动恢复到 1.0.0。当前网站运行正常。

下方显示可行动的失败类别，例如：

- 新容器未能启动
- 数据库迁移校验未通过
- 回环健康检查超时
- 公网鉴权边界验证失败

同时显示安全的错误编号和“重试”按钮。重试创建新任务，不复用已失败任务，也不能覆盖失败审计记录。

### 回滚失败

页面使用最高等级警示：

> 自动恢复未完成，请不要重复更新。请通过 SSH 执行紧急恢复流程。

提供只读的恢复步骤入口和错误编号，但不向浏览器展示完整 Shell 命令输出、服务器目录结构或环境值。此状态下锁定所有更新按钮，直到服务器端确认服务恢复或运维人员显式解除故障锁。

## 更新历史

历史记录每行展示：

- 结果：成功 / 已回滚 / 失败
- `旧版本 → 目标版本`
- 开始时间、耗时
- 触发方式：管理员手动（首版只有这一种）
- 若失败，显示失败阶段和安全原因摘要

展开后展示各阶段耗时、目标 commit、备份是否完成、回滚结果和关联错误编号。默认保留最近 50 条或 90 天，结构化记录存放在服务器持久目录，不随 release 切换丢失。

管理员邮箱可以用于审计，但页面只需显示“当前管理员”；日志中可保存规范化后的管理员标识，不能保存 Cloudflare JWT、Cookie 或身份提供商 token。

## 移动端

管理后台可能从手机访问，更新页面必须能独立完成全部流程：

- 版本卡片与阶段时间线采用单列布局，不使用必须横向滚动的表格。
- 更新主按钮置于卡片底部；确认页可用底部抽屉，按钮至少 44px 高。
- 更新中将当前阶段固定在首屏，已完成阶段折叠，避免长时间线把结果推到页面底部。
- 页面切后台再回来时先从服务端重新同步，不依赖内存状态。
- 网络切换、锁屏和 Cloudflare Access 会话刷新不能导致重复发起任务。
- 高风险回滚按钮不与“重新检查”并排，减少误触。

## 默认策略

| 项目 | 默认值 | 理由 |
| --- | --- | --- |
| 更新通道 | 稳定版 Release | 个人生产环境不应跟随 `main` |
| 检查频率 | 6 小时 + 打开页面时 | 提示及时，但不制造无意义请求 |
| 安装方式 | 管理员手动确认 | 防止无人值守版本破坏邀请码入口 |
| 发布来源 | 固定仓库、固定 tag、明确 commit | 禁止浮动 `latest` 成为生产真相 |
| 数据库备份 | 每次切换前强制成功 | 失败即停止，不提供跳过 |
| 失败处理 | 自动回滚 | 缩短故障窗口 |
| 并发 | 全局仅一个任务 | 防止双击或多设备并行部署 |
| 历史保留 | 50 条或 90 天 | 对个人服务器足够且便于审计 |
| 通知 | 仅管理后台 | 首版不引入邮件/第三方通知配置 |
| 自动安装 | 关闭 | 待生产演练稳定后再评估 |

“重新检查”可以高频限速，但失败不应影响邀请码管理。GitHub 暂时不可达时应显示“暂时无法检查更新，当前版本继续正常运行”。

## 浏览器绝不能看到的内容

更新 API 只返回预定义状态码和脱敏摘要，以下信息不得进入 HTML、JSON、事件流、浏览器控制台或错误堆栈：

- `.env` 内容、Google/Cloudflare 密钥、GitHub token、SSH 凭据
- Cloudflare Access JWT、Cookie、CSRF 值、管理员完整认证断言
- 邀请码明文、设备 token、SQLite 原始数据或数据库备份路径
- Docker inspect 全量结果、完整环境变量、原始 Shell 命令和 stdout/stderr
- 服务器绝对目录、其他 1Panel 站点名称和配置
- Git remote 中可能包含的凭据

允许展示的诊断信息应为固定枚举（如 `health_check_timeout`）、短 commit、版本号、阶段、时间和随机错误编号。更深诊断只允许管理员通过 SSH 查看受权限保护的服务端日志。

## MVP（建议首版实施）

MVP 的目标是把当前可靠的人工发布流程产品化，而不是一次做成通用部署平台：

- 管理后台“版本与更新”页面和导航提示
- 固定 GitHub 仓库的稳定版检查、中文变更摘要和手动更新
- 服务端持久化任务、全局锁、幂等触发、刷新后恢复
- 更新前可信来源校验、配置预检、磁盘检查、SQLite 在线备份
- 旧版本在线构建、不可变 release、唯一镜像标签、最小切换窗口
- 容器、迁移、回环、OpenResty、直连源站和公网 HTTPS 门禁
- 门禁失败自动回滚并验证旧版本恢复
- 分阶段进度、断线重连、安全失败解释、重试
- 最近更新历史和结构化审计
- 桌面与移动端基本可用性
- 单元测试、失败注入集成测试和至少一次生产回滚演练

MVP 不包括自动安装、定时维护窗口、多更新通道、多人审批、邮件通知、跨服务器部署和可编辑 Shell 命令。

## V2 候选

MVP 经过多次真实升级与回滚演练后，再考虑：

- 维护窗口与“下载/构建完成后等待确认切换”
- 稳定版自动安装，但默认仍关闭；仅在备份与全门禁可自动回滚时允许开启
- 预发布通道，必须显著标识且与稳定版隔离
- GitHub Webhook 或发布通知，替代定时检查
- 邮件/Telegram 等成功与失败通知
- 发布制品 checksum、签名与来源证明的可视化
- 更新前在备用回环端口运行更完整的冒烟测试
- 手动回滚到最近一个已验证版本（仅允许兼容的数据库版本）
- release、镜像和备份的可配置保留策略与磁盘容量预测
- 多管理员场景下的发起人、批准人和双人确认

不要在 V2 把页面演变成任意命令执行器；版本来源、操作类型和部署阶段仍应保持白名单化。

## 产品验收场景

1. 管理员发现稳定版，阅读中文摘要，单次确认后更新成功，全程不接触 SSH。
2. 更新时关闭手机页面，稍后在电脑打开，看到同一任务已完成及完整历史。
3. 切换期间管理 API 短暂断连，页面自动重连，不出现误导性的失败或重复任务。
4. 两台设备同时点击更新，服务器只创建一个任务，两边显示同一进度。
5. 备份失败时更新在切换前停止，线上旧版本不受影响。
6. 新版本健康检查失败，系统恢复旧版本并明确提示“当前网站运行正常”。
7. 自动回滚也失败时，系统锁住更新入口并给出安全错误编号和 SSH 紧急恢复指引。
8. 未通过 Cloudflare Access 的请求无法查看当前版本、候选版本、任务状态或历史。
9. 手机锁屏、网络切换、刷新页面后，任务状态仍准确且不会重复提交。
10. 页面和浏览器日志中不存在凭据、邀请码、原始部署命令、环境变量或其他站点信息。

## 第二轮反方审查：最容易“看起来丝滑但实际危险”的三点

以下审查假设管理员会误触、重复点击，手机会切后台，网络会中断，Access 服务也会在切换中重启。单靠按钮禁用、进度动画和“自动重连”并不能证明更新安全。

### 1. “关页也会继续”可能只是视觉承诺

危险点：如果更新任务实际运行在即将被替换的 Access Node 进程中，容器重启时任务、内存锁和事件流会一起消失。手机后台挂起或网络中断后，页面即使恢复轮询，也可能只看到一个无法确认最终状态的旧任务。此时界面看起来平滑，部署却可能停在“新容器已启动、软链接未切换”或“已切换、尚未验证”的中间态。

具体收缩：

- MVP 必须把部署执行器放在 release 和 Access 容器生命周期之外，由稳定的宿主机服务管理；管理页面只提交命令和读取状态。
- 每一步开始前、完成后都写入宿主机持久状态，至少包含任务 ID、目标 revision、当前阶段、切换前版本和最终结果。
- 服务重启后必须先执行恢复判定：根据真实 `current` 指向、容器标签和健康状态重建任务结果，不能只相信上次写入的“进行中”。
- 在完成重启恢复测试之前，产品文案不得写“关闭页面后仍会继续”；只能写“更新已交给服务器处理，可稍后回来查看”。
- MVP 不做任务取消、并行构建或排队，只允许一个明确的活动任务。

### 2. “按钮已禁用”不能阻止重复部署

危险点：浏览器按钮禁用只约束当前页面。双击、刷新重发、两台设备同时操作、Cloudflare Access 重新认证或移动端恢复页面，都可能产生多个请求。若幂等键由浏览器临时生成并在刷新后丢失，服务器可能创建两个构建任务，甚至交错切换和回滚。

具体收缩：

- 服务器以“全局活动任务锁 + 目标 revision 唯一约束”作为真相，不能依赖前端防抖。
- `开始更新` API 必须使用服务器可持久化的幂等语义：相同目标版本在已有活动任务时始终返回同一个任务 ID；不同目标版本返回明确冲突。
- 锁必须跨进程、跨容器重启生效，并带有可审计的租约/接管规则；不能使用 Node 内存布尔值。
- 页面重连后先查询活动任务，再决定是否显示按钮；任何设备看到的状态一致。
- 重试只允许在任务已进入最终失败状态后创建新任务，并记录 `retryOf`，不能“继续使用原任务”或覆盖历史。
- 手动解除故障锁属于 SSH 紧急操作，不在首版页面暴露，避免管理员把真实故障当成“卡住”后强制重入。

### 3. “失败自动回滚”可能对数据库造成二次伤害

危险点：应用镜像和 release 可以回滚，不代表 SQLite schema 和更新期间产生的数据也能无损倒退。若新版本执行不可逆迁移、旧版本无法读取新 schema，或者切换后已有邀请码/会话写入，直接恢复更新前数据库备份会丢失新写入；只回滚容器又可能导致旧代码无法启动。把所有失败都显示成“已自动恢复”会制造虚假安全感。

具体收缩：

- MVP 只允许声明为“可向后兼容”的迁移进入一键更新：旧版本必须能在新 schema 上继续运行，采用先扩展、后清理的迁移纪律。
- Release 清单必须明确标注迁移版本、最低可回滚版本和是否允许自动回滚；元数据缺失时禁止页面更新。
- 自动回滚默认只回滚应用 release，不自动覆盖线上 SQLite。数据库备份用于人工灾难恢复，不能在仍有流量时自动还原。
- 如某版本包含破坏性迁移，必须从普通一键更新中剔除，进入有维护窗口、停止写入、专项备份和人工确认的独立流程。
- 成功文案只有在旧版本恢复并通过门禁后才能写“已恢复”；否则必须显示“需要人工恢复”，不能把“已触发回滚”当成“回滚成功”。
- 上线前至少演练三类故障：构建失败（未切换）、切换后健康失败（应用回滚）、迁移后旧版本不兼容（应在预检阶段被阻止）。

## 必须由用户决定的唯一产品问题

**首版是否允许服务器发现稳定版后无人值守自动安装，还是必须由管理员进入后台并手动确认？**

建议选择“只自动检查，管理员手动确认安装”。它保留绝大多数丝滑体验，同时把版本变更、迁移和短暂服务切换放在管理员知情的时间点。若选择无人值守自动安装，维护窗口、通知、迁移兼容声明、故障升级和自动恢复证明都必须提前进入 MVP，范围和上线风险会显著扩大。
